# Per-file corpus scores

`docs/corpus-scores.json` and `docs/corpus-scores.csv` publish the **per-file
scores behind every aggregate** in [`validation-corpus.md`](./validation-corpus.md).
They exist so a reader can recompute the headline figures instead of trusting
the summary table.

Both files are generated by `scripts/validate_corpus.py`, in the same run and
under the same leak scan that produces the report. Do not hand-edit them.

> Coverage counts which of 23 controls the prompt **text** states. It is not
> quality, not safety, not certification, and not evidence of runtime behavior.
> A low score means the text is silent on a control, not that the product lacks
> it. Read [`validation.md`](./validation.md) before quoting any of this.

## What is in the corpus

356 prompts, from two upstream collections pinned by commit:

| Corpus key | Files | Upstream |
| --- | --- | --- |
| `gpt_store` | 273 | [linexjlin/GPTs](https://github.com/linexjlin/GPTs) |
| `production` | 83 | [x1xhlol/system-prompts-and-models-of-ai-tools](https://github.com/x1xhlol/system-prompts-and-models-of-ai-tools) |

The exact SHAs live in `generated_from` in the JSON. `ruleset` records the
ruleset id the scores were produced under (`crewscore-hygiene@0.6.0` at the time
of writing); scores from different rulesets are not comparable.

## Row schema

`schema_version` is `1.0`. Every entry in `files` carries exactly these keys —
the schema is a whitelist, enforced by `tests/test_corpus_scores.py`:

| Key | Meaning |
| --- | --- |
| `corpus` | `gpt_store` or `production` |
| `file_id` | 16 hex characters — `sha256(path)[:16]`, deterministic, not reversible |
| `score` | Overall coverage, 0–100 |
| `bytes` | Length of the prompt text |
| `dimensions` | Per-dimension coverage for the 8 governance dimensions |
| `controls_fired` | Sorted control keys that matched, drawn from the 23 in `controls` |

The CSV is a flattened view of the same rows for spreadsheet use. It omits
`dimensions` and joins `controls_fired` with `|`; the JSON is authoritative.

## Why there is no filename

**A path in this corpus is prompt content wearing a different hat.** In the
GPT-Store collection the filename *is* the assistant's name, and the prompt text
restates it — so publishing paths would redistribute exactly what the upstream
licences reserve to their maintainers. The leak scan caught this on 2026-08-24,
rejecting a path whose window read `T Customizer, File Finder & JSON Action`.

So the rows carry an opaque `file_id` instead, and no path, no prompt text, no
matched span, and no line number. `test_rows_carry_derived_data_only` fails the
build if any other key appears. The derived scores are ours to publish; the text
behind them is not.

To map an id back to a file you must already hold the pinned upstream and
recompute `sha256(path)[:16]` yourself.

## Reproducing the aggregates

```bash
python scripts/validate_corpus.py   # regenerates the report and both score files
pytest tests/test_corpus_scores.py  # proves the rows and the report agree
```

That test is the reason this data is worth publishing. It re-derives the
distribution table, the per-control hit counts, and the never-fired list from
the rows alone, and asserts they equal the published report — so the rows and
the summary are provably the same computation. It also pins provenance: the
SHAs and ruleset in the rows must match the report's.

The tests skip, rather than fail, when the generated files are absent — run the
harness first.
